# Universal Workspace — дополнение к Design Engine

Срез концепции 25.09.2026. Этот документ дополняет DESIGN.md и PHILOSOPHY.md и фиксирует гипотезы для прототипирования.

## 1. Одна структура — несколько проекций

Graph / Table / Board / Chat — разные представления одних объектов, а не независимые документы.

- Graph показывает процесс, зависимости и параллельную работу.
- Table показывает состояние проекта: задача, статус, исполнитель, последнее изменение, заметка.
- Board сохраняет свободную пространственную раскладку и пространственную память.
- Chat хранит центральную линию разговора, решений и выводов.

Изменение объекта в одной проекции должно отражаться в остальных. Таблица проекта по возможности возникает из самой работы, а не требует отдельного ручного обслуживания.

## 2. Центральный диалог и параллельная работа

Базовый позвоночник рабочего пространства — диалог человека с основной моделью. Каждое сообщение остаётся отдельным визуальным блоком. Из любой точки разговора могут расти параллельные ветки агентов, инструментов и процессов.

Результат — самостоятельный объект. Его можно вернуть в центральный диалог автоматически либо явно связать с нужной точкой как контекст.

## 3. Граф до, во время и после выполнения

Граф может быть собран заранее вручную или предложен моделью.

```text
PLAN → REVIEW → RUN → EXECUTION → RESULTS → HISTORY
```

**Граф = план до выполнения + интерфейс во время выполнения + история после выполнения.**

Исполненная нода при исключении из актуального пути не исчезает бесследно: она становится неактуальной/серой и остаётся частью истории. Неисполненный черновик можно удалить.

Для прототипа нужен малый алфавит нод. Кандидаты: message, task, tool, agent/executor, object/data, result, group. Сложность строится группами, а не десятками структурных типов.

## 4. Semantic zoom

Зум меняет не только размер, но и уровень абстракции:

```text
точка / силуэт
→ иконка
→ название
→ состояние
→ содержимое
→ внутренний граф
→ команда / лог / сырые данные
```

При отдалении участок работы может собираться в макроноду. При приближении она раскрывает внутреннюю структуру.

**Чем ближе к объекту, тем ближе к данным и технической реализации.**

## 5. Пространственная грамматика

Для process-графов основной поток рассматривается сверху вниз: начало и намерение выше, развитие и результат ниже. Горизонтальное пространство используется для параллельных веток и связанных материалов.

Это сильная гипотеза для process-графов, а не обязательный закон для любого пространственного графа.

## 6. Физический отклик

Интерактивные элементы должны ощущаться предметами, когда это помогает понять действие.

- кнопка визуально утапливается при нажатии;
- переключатель имеет различимые положения;
- соединение защёлкивается;
- запуск показывает движение исполнения;
- результат появляется из породившего его процесса;
- сворачивание группы собирает элементы внутрь;
- движение используется для реального изменения состояния, а не как украшение.

## 7. Визуальный мир как память

У сложного приложения может быть собственный визуальный мир: метафора, персонажи, семейства, места и характерные предметы. Его задача — усиливать пространственную и ассоциативную память.

Порядок:

```text
функция → группа → метафора → визуальный мир → форма
```

Сначала определяется смысл функции. Образ появляется после него и не должен заставлять угадывать назначение.

Разные продукты могут иметь разный визуальный мир при общей UX-грамматике. Игры и настольные системы полезны как источник принципов группировки: устойчивые семейства, сильные силуэты, ограниченный набор примитивов, узнаваемые места и богатые комбинации.


## 8. Главный экран как газета

Главный экран Cloudberry — не рабочая панель и не каталог проектов. Это **обзор всего мира через хронологию последних событий**.

Базовая метафора — газета / лента новостей по всем отделам.

Принцип:

> **Сначала показывается то, что произошло последним, независимо от проекта.**

Поэтому рядом могут оказаться совершенно разные вещи: новый мем, завершённый рендер, изменение на сервере, готовый пост, результат агента или обновление другого проекта. Это не случайная сортировка — порядок задаёт время события, а разнообразие возникает естественно из жизни разных отделов.

Старые события не исчезают: они уходят ниже по ленте и остаются доступными прокруткой.

### Одна новость

Новость может быть достаточно развёрнутой, потому что главный экран — это режим чтения и изучения, а не только быстрый статус.

Минимальный состав:

- проект / отдел;
- заголовок;
- время;
- превью, если оно есть;
- краткое описание того, что произошло;
- при необходимости — заметка от агента;
- действие: «ОТКРЫТЬ», «ПРОДОЛЖИТЬ», «ПОСМОТРЕТЬ РЕЗУЛЬТАТ» или другое короткое бытовое действие.

Размер новости не обязан быть одинаковым для всех событий. Важный или визуальный результат может занимать больше места, мелкое событие — меньше.

### Переход в работу

Газета — это **первый слой** Cloudberry.

Когда пользователь решает начать новую работу или перейти к конкретному результату, он покидает обзорный слой и входит в соответствующую рабочую комнату / мастерскую.

Схема:

```text
ГАЗЕТА / ОБЗОР МИРА
        ↓
выбор события / проекта / нового действия
        ↓
РАБОЧАЯ КОМНАТА / МАСТЕРСКАЯ
```

Главный экран отвечает на вопрос:

> **«Что произошло и куда мне сейчас идти?»**


## 9. Две формулы

> **Работа сама создаёт своё представление.**

> **Человек управляет намерением; система управляет сложностью исполнения.**


## 10. Product → knowledge loop

Design Engine и UX-библиотека не являются архивами, которые только читают перед новой задачей. Реальный продукт должен возвращать в них проверенные выводы.

Базовый цикл:

```text
design canon / UX patterns
        ↓
конкретный продукт
        ↓
реальное использование / review
        ↓
отделить project-specific от reusable
        ↓
UX-паттерн → ux-lib
общий design principle → design-engine
```

Правила:

- продукт остаётся source of truth для своей реализации;
- конкретные классы, форматы данных, названия экранов и предметная логика не переносятся в общий canon;
- наблюдение сначала фиксируется как гипотеза / proposed pattern;
- статус повышается только после реального использования или повторного применения;
- обновления shared-knowledge делаются отдельно от продуктовых коммитов, чтобы история доказательств не смешивалась с реализацией;
- не каждый удачный локальный приём обязан становиться общим правилом.

Цель — чтобы каждый следующий интерфейс начинался не с нуля, но и чтобы библиотека не превращалась в свалку деталей прошлых проектов.

## 11. Triage workspace: очередь → решение → видимые корзины

Для задач последовательного review, где человек сортирует множество объектов по небольшому числу исходов, полезна пространственная модель:

```text
UNREVIEWED
    ↓
decision
    ↓
bucket A | bucket B | bucket C
```

Смысл не в конкретных KEEP / MAYBE / REJECT, а в четырёх свойствах:

1. **Результат решения виден пространственно.** Объект исчезает из очереди и появляется там, куда его отнесли.
2. **Главные места стабильны.** Очередь и корзины не меняют положение между решениями.
3. **UI — проекция состояния.** Не создавать параллельную UI-базу только ради визуального переноса.
4. **Решение обратимо.** Один жест решения соответствует одной записи Undo и возвращает объект в предыдущее место.

Для image-review центральный объект может оставаться крупным, а уже разобранные результаты — уплотняться в thumbnails / masonry. Это направление должно проверяться на реальной скорости работы и не является требованием для любого интерфейса со статусами.

**Первая проверка (2026-10-02).** `knowledge_app` Review UI v1.5: один пользователь, одна доска (100 объектов) и тестовые копии; финальный вид принят. Подтвердились свойства 1–4 и два уточнения: управление решением живёт в самих корзинах, а не полосой снизу; причина решения — вложенная цель внутри корзины, групп мало (3, не 9). Скорость не измерялась. Статус остаётся DIRECTION до повторного применения в другом продукте. Детали — ux-lib PT-08 (tested) и PT-09 (tested).
